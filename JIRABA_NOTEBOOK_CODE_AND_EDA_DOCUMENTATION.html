4. Mathematical Formula Reference

1. Class Imbalance Ratio

$$\text{Imbalance Ratio} = \frac{N_{\text{legitimate}}}{N_{\text{fraud}}} = \frac{6,354,407}{8,213} \approx 773.7 : 1$$

2. Sender Double-Entry Accounting Invariant

$$\text{Error}{\text{orig}} = (\text{oldbalanceOrg} - \text{newbalanceOrig}) - \text{amount}$$ $$\text{orig_balance_mismatch} = \begin{cases} 1 & \text{if } |\text{Error}{\text{orig}}| > \epsilon \ 0 & \text{if } |\text{Error}_{\text{orig}}| \le \epsilon \end{cases} \quad (\text{where } \epsilon = 0.01)$$

3. Rule Engine Performance Metrics

$$\text{Precision} = \frac{TP}{TP + FP} = \frac{16}{16 + 0} = 1.0000 \quad (100.0\%)$$ $$\text{Recall} = \frac{TP}{TP + FN} = \frac{16}{16 + 8,197} = \frac{16}{8,213} \approx 0.001948 \quad (0.19\%)$$ $$F_1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}} \approx 0.003889$$

4. Cyclical Diurnal Time Encoding

$$\text{hour} = \text{step} \pmod{24}$$ $$x_{\sin} = \sin\left(\frac{2\pi \cdot \text{hour}}{24}\right), \quad x_{\cos} = \cos\left(\frac{2\pi \cdot \text{hour}}{24}\right)$$

PaySim Mobile Money / UPI Fraud Detection: In-Depth Technical Documentation

Comprehensive Cell-by-Cell Data Science & Machine Learning Engineering Analysis of Jiraba.ipynb

Executive Architectural & Domain Overview

This document provides a senior-level data scientist and machine learning engineer walkthrough of the Jupyter Notebook Jiraba.ipynb.

1. The Dataset: PaySim Synthetic Financial Simulator

The dataset loaded in this notebook (paysim1/PS_20174392719_1491204439457_log.csv) originates from PaySim, an agent-based financial simulator modeled on actual transactional logs from a mobile money service operated in an African country (originally published by Lopez-Rojas et al.). - Total volume: $6,362,620$ transactions. - Simulation Duration: 743 discrete time steps (where $1\text{ step} = 1\text{ hour}$, spanning $\approx 31$ days). - Core Business Goal: Detect unauthorized account takeover and fraudulent transfers/cashouts under severe class imbalance ($0.1291\%$ fraud prevalence).

2. The Anatomy of Fraud in the System

The exploratory analysis uncovers the primary fraudulent modus operandi: 1. Compromise / Account Takeover: Fraudsters gain access to a customer account (nameOrig). 2. Account Liquidation via TRANSFER: The fraudster initiates a TRANSFER of the entire balance (amount == oldbalanceOrg, reducing newbalanceOrig to 0.00). 3. Immediate Liquidation via CASH_OUT: The funds received at a drop account (nameDest) are immediately converted to physical cash via a CASH_OUT transaction of the exact same amount. 4. Complete Absence in Other Types: Fraud occurs exclusively in TRANSFER ($4,097$ cases) and CASH_OUT ($4,116$ cases). Transactions of type PAYMENT, CASH_IN, and DEBIT contain zero instances of fraud in this entire $6.36$-million-row dataset.

3. Naive Rule-Based Alert System Failure (isFlaggedFraud)

The legacy business rule flags transactions where amount > 200,000 in a single transfer. Out of $8,213$ actual frauds, the rule flags only $16$ transactions ($0.19\%$ Recall). While its Precision is $100\%$ ($0$ False Positives), its inability to detect $99.81\%$ of attacks renders it ineffective in production without ML intervention.

Cell 48: Mathematical Precision & Recall Calculation for Rule Engine

  • Cell Type: Code

  • Source Code: ```python actual_fraud = df['isFraud'] == 1 flagged = df['isFlaggedFraud'] == 1
